1 System Overview

CodeLens is a GitHub repository analysis tool. A user pastes a repo URL, and the system fetches the codebase via GitHub API, generates a comprehensive 5-section architecture document using a single LLM call, caches it in PostgreSQL, and displays it in a modern dark-theme UI with zoomable Mermaid diagrams and an interactive chat.

2 Why This Design

Why GitHub API Instead of Traditional RAG?

✓ Direct API Approach (What We Use)
  • Direct, precise file retrieval via GitHub REST API
  • No embedding costs (free GitHub API)
  • Code structure preserved (whole files, not chunks)
  • No vector database needed
  • Works perfectly for single-repo analysis
✗ Traditional RAG (Embeddings + Vector Search)
  • Semantic chunk retrieval (not precise)
  • Embedding API costs money
  • Chunking breaks code structure
  • Requires FAISS/Pinecone/Weaviate
  • Better for large document collections, not single repos

Why Cerebras?

Free tier. The project budget is zero. Cerebras offers a generous free API tier with the zai-glm-4.7 model. It's fast (optimized inference) and supports both chat completions and tool-use. No paid providers, no credit card.

Why Plain JavaScript (not TypeScript)?

Speed of iteration. The frontend is a relatively simple SPA — URL input, markdown rendering, a tree view, a chat panel. TypeScript adds type-checking overhead that isn't needed for this scope. Plain JSX in Vite works out of the box. All files are .jsx / .js.

Why PostgreSQL is Optional?

Zero-config local development. The system checks DB_AVAILABLE at startup. If PostgreSQL isn't running or psycopg2 isn't installed, every DB operation returns None or skips silently. The frontend analysisCache Map prevents duplicate requests within a session. This means developers can run the project without setting up a database.

Why No README Fallback?

Many repos have no README or have an empty one. Instead of failing, the system falls back through: GitHub description → topics array → package.json description → pyproject.toml description → source file docstrings. This was added after testing with repos like thrashr888/no-readme.

Why Recursive Source File Fetching?

The first version of repo_fetcher.py only read top-level files. Repos like Flask have source code in src/flask/*.py subdirectories. The fix: _fetch_code_files_recursive() scans all source directories up to 3 levels deep. This increased source file count from 0 to 50+ for complex repos.

Step 3: Fetch Repository Data (Parallel)

If no cache, repo_fetcher.py fetches everything from GitHub in parallel using asyncio.gather():

    validate_repo(url, github),
    fetch_file_tree(github, url),
    fetch_key_files(github, url, tree),
    fetch_source_files(github, url, tree),
)

Step 4: Build LLM Prompt

hybrid_prompts.py combines everything into a single prompt:

The prompt contains: repo metadata + file tree + config file contents + source file contents. Everything the LLM needs to analyze the codebase.

Step 5: LLM Generates 5 Sections

hybrid_analyzer.py calls Cerebras with the prompt. The LLM generates all 5 sections in one response:

## Section 1: Purpose & Scope
Flask is a lightweight WSGI web application framework...

## Section 2: Repository Layout
```
flask/
├── src/flask/        # Core framework source
├── tests/            # Test suite
...
```
Pattern: modular layout

## Section 3: Source Layer (Tech Stack)
| Category | Technology | Evidence |
|----------|------------|----------|
| Language | Python | pyproject.toml |
| Framework | Flask | src/flask/__init__.py |

## Section 4: Architecture
```mermaid
flowchart TD
    A[Client Request] --> B[WSGI Server]
    B --> C[Flask App]
...```

## Section 5: RPC Protocol
Flask uses WSGI protocol...

Takes ~10-15 seconds. The output is structured text with headers that the parser can split into sections.

Step 6: Parse Sections

parse_sections() splits the LLM output by headers:

# hybrid_analyzer.py

# Find all section headers
headers = re.findall(r'## (?:Section \d+: )?(.+?)$', text, re.MULTILINE)

# Split by headers, extract content between them
for i, header in enumerate(headers):
    start = text.index(header)
    end = text.index(headers[i+1]) if i+1 < len(headers) else len(text)
    sections[header] = text[start:end]

Returns a dictionary with 5 keys: purpose_scope, repo_layout, source_layer, tech_stack, architecture_text.

Why React + Vite (not Next.js)?

SPA is sufficient. The frontend is a single-page app that talks to a FastAPI backend. There's no need for SSR, server components, or Next.js API routes. Vite gives faster dev server startup, smaller bundle size, and simpler deployment (static files). React Router v6 handles routing.

Why Dark Theme?

Developer tools should be easy on the eyes. The design uses slate-900 gradient backgrounds, emerald (#34d399) as the primary accent color, and Inter + JetBrains Mono fonts. The theme is consistent across all pages.

7 LLM Integration (Cerebras)

For Analysis

One call, all 5 sections. The hybrid_analyzer.py builds a single prompt containing repo metadata, file tree, config files, and source files. Cerebras generates all sections in one response. The output is parsed by parse_sections() which looks for ## Section N: or ## Name headers.

For Chat

One call per question. chat_with_repo() in main.py fetches repo context (analysis cache + key files + source files), builds a system prompt + user message, and calls Cerebras once. No agentic tool-use loop.

Model

zai-glm-4.7 — the only Cerebras model with tool-use support. Used for both analysis and chat. Free tier, no rate limits for reasonable usage.

API Usage

from cerebras.cloud.sdk import Cerebras

client = Cerebras(api_key=os.getenv("CEREBRAS_API_KEY"))

response = client.chat.completions.create(
    model="zai-glm-4.7",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt},
    ],
    max_tokens=4096,
)

answer = response.choices[0].message.content

8 Anti-Hallucination System

The LLM is given strict rules in the system prompt. Violations produce incorrect output, so these rules are critical:

RuleWhat It Means
Every statement must cite a file pathIf the LLM says "uses React", it must say which package.json has "react"
Use ONLY provided dataNo guessing about functions, classes, or APIs not in the fetched files
"Not found" for missing infoIf a README is empty, say so. Don't invent a purpose.
No invented file namesDon't reference src/auth.js if it wasn't in the file tree
Tech stack from config files onlyOnly list technologies found in package.json, requirements.txt, etc.

System Prompt (Key Section)

"CRITICAL RULES - VIOLATION IS NOT ACCEPTABLE:
1. You are given EXACT file contents and directory structure from a real GitHub repository.
2. You MUST use ONLY the data provided below. Every statement you make MUST reference
   a specific file path from the provided data.
3. If information is not present in the provided files, say 'Not found in provided files'
   — DO NOT GUESS, DO NOT HALLUCINATE.
4. Do NOT invent file names, function names, class names, or any code that is not
   explicitly shown in the provided data.
5. For technology stack: only list technologies that are EXPLICITLY present in the
   provided config files (package.json, requirements.txt, etc.) or source code."

14 Interview Questions & Answers

Every question an interviewer could ask about this project, from architecture to implementation details.

A. System Design & Architecture

Q1: Walk me through the high-level architecture of this project.

CodeLens is a three-tier system: React/Vite SPA (frontend) → FastAPI backend (orchestration) → External services (GitHub API, Cerebras LLM, PostgreSQL). The frontend sends a GitHub URL to the backend. The backend fetches repo data via GitHub API in parallel, builds a single prompt with all the context, calls Cerebras LLM once to generate 5 analysis sections, caches the result in PostgreSQL, and returns it. The frontend renders it as a wiki page with zoomable Mermaid diagrams and markdown content.

Q2: Why did you choose a hybrid approach over an agentic loop?

The first version used an agentic loop — the LLM would decide which MCP tool to call, execute it, get the result, and loop (8+ sequential LLM calls, 2-3 minutes per analysis). I replaced it with a hybrid approach: one LLM call generates all 5 sections at once (~15 seconds). Why: (1) predictable latency, (2) lower token cost (single prompt vs 8+), (3) works with Cerebras free tier without tool-use overhead, (4) simpler codebase, (5) more reliable — no risk of the agent looping or picking wrong tools.

Q3: What are the trade-offs of the hybrid approach?

Pros: Fast, cheap, predictable, simple. Cons: (1) The LLM can't dynamically explore the codebase — it only sees what we pre-fetch, so it might miss important files in large repos. (2) The context window is limited — we truncate source files to ~1500 chars each, which may lose nuance. (3) No iterative refinement — the agentic approach could read a file, realize it needs more context, and fetch another. The hybrid approach is a single shot. Mitigation: We fetch config files + all source files recursively, and the LLM prompt is carefully designed to work with the available data.

Q4: How does this system handle scalability?

Per-request: Each analysis takes ~15 sec (GitHub fetch + LLM call). The DB cache means repeat requests are instant. Concurrency: FastAPI is async, so it handles multiple requests without blocking. GitHub API rate limits (5000 req/hr with token) are the bottleneck for many concurrent analyses. Horizontal scaling: The backend is stateless — just add more instances behind a load balancer. The DB is the shared state. LLM scaling: Cerebras handles inference; we don't control it, but their free tier is generous for moderate usage.

Q5: How would you improve this system if you had more time?

(1) Streaming: Use WebSocket/SSE to stream LLM output to the frontend for better UX. (2) Smarter fetching: Use the LLM to decide which files to read (agentic fetch) before the single analysis call. (3) Embeddings: Add vector search for the chat system so it can retrieve relevant code snippets instead of truncating. (4) Rate limiting: Add request queuing for high traffic. (5) Testing: Add integration tests for the full pipeline. (6) Monitoring: Add Prometheus metrics for LLM latency, GitHub API usage, cache hit rate.

B. Backend Design

Q6: How does the GitHub API integration work?

tools/github_api.py wraps the GitHub REST API. It uses httpx.AsyncClient for non-blocking HTTP calls. Key methods: validate_repo() (checks accessibility, returns metadata + topics), list_directory() (lists folder contents), get_file_content() (reads file), get_file_tree() (recursive directory listing with depth limit). The repo_fetcher.py calls these in parallel using asyncio.gather() for speed.

Q7: How do you handle GitHub API rate limits?

Without authentication: 60 requests/hour. With a token: 5000/hour. The system uses a GITHUB_TOKEN from .env if available. We also minimize calls by: (1) caching results in PostgreSQL, (2) fetching file trees once (not per-section), (3) only reading config files by name (not scanning all files). If rate-limited, the system returns an error with a clear message.

Q8: Explain the database schema and why you chose that design.

Single table repo_analysis with repo_url as primary key. Each column stores one analysis section as TEXT. UPSERT on conflict updates all fields. Why TEXT type: Analysis sections can be long (markdown, mermaid code), and TEXT has no length limit. Why no normalized tables: The data is always accessed as a whole — we never query "just the tech stack for repo X". One row per repo is simpler and faster. Why no updated_at: Initial version had it but the column wasn't being set, causing INSERT failures. Removed it since created_at is sufficient for cache invalidation.

Q9: Why is the database optional? How does the fallback work?

For local development, requiring PostgreSQL adds setup friction. The system checks: (1) Is psycopg2 installed? (2) Can we connect? If either fails, DB_AVAILABLE = False. Every DB operation checks this flag and returns None or skips silently. The frontend cache (analysisCache Map) prevents duplicate requests within a session. Without DB, each page load regenerates the analysis (~15 sec), but it works.

Q10: How does the section parser work?

hybrid_analyzer.py calls Cerebras, gets the full response, then parse_sections() splits it. It uses regex to find section headers: ## Section N: Name, ## Name, or # Name. Each section's content is everything between one header and the next. If a section isn't found, it defaults to "Section not generated." The parser also strips the first header line from each section's content (since the wiki page renders the header separately).

Q11: How does the recursive file fetcher work?

_fetch_code_files_recursive() takes a list of source directories (e.g., ["src", "lib", "app"]) and recursively scans them for source files (.py, .js, .ts, .go, .rs, .java, .rb, .php, .c, .cpp, .h). It uses asyncio.gather() to read multiple files in parallel. Depth is limited to 3 levels to avoid infinite recursion. Files are truncated to ~3000 chars each to stay within LLM context limits.

C. LLM Integration

Q12: How do you prevent LLM hallucination?

Three layers: (1) Strict system prompt: Rules like "every statement must cite a file path", "use ONLY provided data", "say 'Not found' for missing info". (2) Constrained input: We only feed the LLM actual file contents and directory structures — no vague descriptions. (3) Post-processing: The section parser checks for empty/missing sections and falls back to defaults. The LLM model zai-glm-4.7 also tends to be conservative and follow instructions well.

Q13: How do you handle context window limitations?

Cerebras models have a context window (varies by model). We manage it by: (1) Truncating each source file to ~3000 chars, (2) Limiting to 10 key config files + 10 source files, (3) Truncating analysis context in chat to ~1000 chars per section, (4) Using max_tokens=4096 for output. If the input exceeds the window, the API call may fail — we catch this and return an error. For large repos, this means some files are missed, which is a known trade-off.

Q14: Why Cerebras specifically? What about OpenAI, Anthropic, etc.?

Budget constraint: The project uses zero paid services. Cerebras offers a free API tier with decent rate limits. OpenAI/Anthropic require paid API keys. Model choice: zai-glm-4.7 is the only Cerebras model with tool-use support (though we only use chat completions now). Speed: Cerebras has optimized inference infrastructure. Trade-off: Smaller model means lower quality outputs compared to GPT-4 or Claude, but the strict prompt compensates.

Q15: How would you switch to a different LLM provider?

llm_utils.py wraps the Cerebras client. To switch: (1) Create a new client class for the target provider (e.g., OpenAIClient), (2) Implement the same chat.completions.create() interface, (3) Update the model name and API key env var. The prompts in hybrid_prompts.py are provider-agnostic — they're just strings. The only Cerebras-specific code is in main.py (chat) and hybrid_analyzer.py (analysis).

Q16: How do you parse the LLM output into structured sections?

The LLM is prompted to output sections with headers like ## Section 1: Purpose & Scope. The parser uses regex patterns: r'## Section \d+: (.+?)$', r'## (.+?)$', r'# (.+?)$'. It finds all headers, sorts by position, and extracts content between consecutive headers. If the LLM outputs in a slightly different format (e.g., missing "Section N"), the fallback patterns still catch it. This makes the parser robust to minor LLM output variations.

D. Frontend Architecture

Q17: How does the frontend prevent duplicate API calls?

api/client.js maintains an in-memory analysisCache (a Map). Before every fetch, it checks if the URL+forceRefresh key exists in the cache. If yes, returns the cached result. If no, fetches and stores. Also: React StrictMode was removed from main.jsx because it causes double-rendering in dev mode, which triggers duplicate API calls. The cache key includes force_refresh so manual refreshes bypass it.

Q18: How does the Mermaid diagram zoom/pan work?

MermaidDiagram.jsx uses CSS transforms: transform: scale(${zoom}) translate(${panX}px, ${panY}px). Zoom is controlled by: (1) buttons (+/-/reset), (2) Ctrl+Scroll wheel (with event.preventDefault() to prevent page zoom), (3) pinch on trackpad. Pan uses onMouseDown/Move/Up events tracking delta movement. The fullscreen modal uses a fixed-position overlay with backdrop-filter: blur(8px) and ESC key listener to close.

Q19: How does the MarkdownRenderer handle code blocks with tree characters?

Early bug: code blocks were being skipped entirely because the regex for inline code (`code`) was consuming backticks before the code block parser ran. Fix: parse code blocks first (match ```...```), extract their content, wrap in <pre><code>, then process inline markdown on non-code text. Tree characters (├──, └──, │) render correctly inside <pre> blocks because whitespace is preserved.

Q20: Why remove React StrictMode?

React StrictMode intentionally double-invokes effects and state updates in development to catch bugs. This caused analyzeRepository() to fire twice on mount, sending two POST requests to the backend. The second request would either hit the DB cache (wasteful) or trigger a second LLM call (expensive). Removing StrictMode is acceptable because: (1) the app is simple enough that double-rendering bugs are unlikely, (2) the performance cost of duplicate API calls outweighs StrictMode's benefits, (3) production builds don't have StrictMode double-rendering anyway.

Q21: How does the WikiPage handle navigation without a header bar?

The WikiPage has no top header — it fills the entire viewport. Navigation is via: (1) WikiTreeView sidebar (collapsible folder tree + section links), (2) Breadcrumb at the top (CodeLens / owner/repo), (3) Back button to return to HomePage. The tree view uses onClick to scroll to sections via document.getElementById(sectionId).scrollIntoView(). The chat panel floats at the bottom with position: fixed.

E. API Design

Q22: What are the API endpoints and their responsibilities?

POST /api/analysis: Accepts { repo_url, force_refresh }. Checks DB cache, fetches from GitHub if miss, generates LLM analysis, stores in DB, returns all sections. GET /api/analysis/{repo_url}: Retrieves cached analysis from DB (read-only). POST /api/chat: Accepts { repo_url, question }. Builds context from cached analysis + key files, makes single LLM call, returns answer. All endpoints return JSON. CORS allows localhost:5173 and localhost:3000.

Q23: Why use POST for analysis instead of GET?

GET requests should be idempotent and cacheable. Analysis is expensive (LLM call, GitHub API calls) and not idempotent (force_refresh bypasses cache). POST allows: (1) request body with force_refresh flag, (2) clear indication that the server performs side effects (LLM call, DB write), (3) no URL length limits (GitHub URLs can be long). GET /api/analysis/{url} is available for read-only cache lookups.

Q24: How does error handling work across the stack?

Backend: Each function catches exceptions and returns meaningful errors. GitHubAccessError for repo access issues. FastAPI HTTPException with status codes (404 for not found, 500 for internal errors). DB errors are logged but don't crash the request (graceful degradation). Frontend: client.js checks response.ok and throws with the error detail. Components catch errors and display them in the UI (e.g., "Failed to analyze repository"). The chat panel shows error messages inline.

F. Security

Q25: How do you handle API keys and secrets?

Backend: Keys stored in .env file (gitignored). Loaded via python-dotenv. Never hardcoded. CEREBRAS_API_KEY and GITHUB_TOKEN are the two secrets. Frontend: No secrets — it only talks to the FastAPI backend. DB credentials: Also in .env, with sensible defaults for local dev. Production: Use environment variables injected by the deployment platform (e.g., Vercel, Railway).

Q26: What CORS configuration do you use?

allow_origins=["http://localhost:5173", "http://localhost:3000"] — only the frontend dev servers. allow_methods=["*"] and allow_headers=["*"] for flexibility during development. allow_credentials=True to support cookies if needed. Production: Would restrict origins to the actual deployed frontend URL.

Q27: Is there any input validation?

Pydantic models: AnalysisRequest and ChatRequest validate input types. repo_url is a string, force_refresh is a boolean. URL validation: validate_repo() checks that the URL points to a valid, accessible GitHub repository. SQL injection: Not possible — we use parameterized queries (%s placeholders) with psycopg2. XSS: The frontend renders markdown as HTML — MarkdownRenderer doesn't use dangerouslySetInnerHTML for user input, only for LLM-generated markdown.

G. Performance & Optimization

Q28: How do you optimize the analysis pipeline for speed?

Parallel fetching: asyncio.gather() fetches config files, source files, and repo metadata simultaneously. Single LLM call: All 5 sections in one prompt (vs 8+ calls in the old agentic approach). DB caching: Repeat requests are instant. Frontend cache: In-memory Map prevents duplicate requests. File truncation: Source files capped at ~3000 chars to reduce prompt size and LLM processing time. Depth limit: File tree limited to 3 levels to avoid fetching too many files.

Q29: What are the bottlenecks in this system?

GitHub API: Each file read is an API call. Large repos with many files hit rate limits (5000/hr with token). LLM latency: Cerebras inference takes ~10-15 seconds for a large prompt. Network: Each GitHub API call has ~200-500ms latency. DB: PostgreSQL writes are fast (~5ms) but reads with cold cache are slow (full analysis regeneration). Frontend: Mermaid rendering can be slow for complex diagrams (~2-3 sec).

Q30: How would you handle 100 concurrent users analyzing different repos?

Current bottleneck: GitHub API rate limits (5000/hr). With 100 concurrent users, each analysis uses ~10-20 API calls, so ~1000-2000 calls in a short window. Solutions: (1) Request queuing with rate limiting, (2) Multiple GitHub tokens for rotation, (3) Aggressive DB caching (most repos will be repeat requests), (4) Horizontal scaling of FastAPI instances, (5) Background job queue (Celery/RQ) for analysis generation.

H. Testing & Quality

Q31: How would you test this system?

Unit tests: Test parse_sections() with various LLM output formats. Test build_hybrid_prompt() with mock repo data. Test MarkdownRenderer with edge cases. Integration tests: Test the full API pipeline with a mock GitHub API and mock LLM. Test DB operations with a test database. E2E tests: Use Playwright/Cypress to test the full flow: enter URL → see analysis → use chat. Mocking: Mock Cerebras API ( expensive to call in tests) and GitHub API (rate limits).

Q32: What are the main edge cases you've handled?

(1) No README: Fallback to GitHub description, topics, package.json. (2) Empty/private repos: GitHub API returns error, caught and surfaced. (3) DB unavailable: System works without caching. (4) LLM output format variations: Parser uses multiple regex patterns. (5) Large repos: File truncation + depth limits. (6) Rate limits: Token-based authentication increases limits. (7) Invalid URLs: Pydantic validation + GitHub API check. (8) Network errors: try/except with meaningful error messages.

I. Key Technical Decisions

Q33: Why plain JavaScript instead of TypeScript?

Trade-off: type safety vs development speed. For this project: (1) The frontend is relatively simple (5 components, 2 pages), (2) No team to benefit from type contracts, (3) Vite works with plain JSX out of the box, (4) Adding TypeScript means config files (tsconfig.json), type annotations on every component, and stricter build steps. If the project grows to 20+ components, TypeScript would be worth adding.

Q34: Why not use embeddings/vector search for the chat system?

Embeddings (e.g., OpenAI embeddings + FAISS) would enable semantic search over the codebase. But: (1) Requires a paid embedding API, (2) Adds complexity (chunking, indexing, similarity search), (3) The current approach (pass analysis + key files as context) works for most questions. When embeddings would help: Questions like "find all functions related to authentication" that need semantic matching across many files. The current system can only answer questions about files it has in context.

Q35: Why use FastAPI instead of Flask or Django?

FastAPI advantages: (1) Native async support (critical for GitHub API + LLM calls), (2) Auto-generated OpenAPI docs, (3) Pydantic request/response validation, (4) Type hints as documentation. Flask: No native async, would need aiohttp or celery for background tasks. Django: Too heavy — includes ORM, admin, auth that we don't need. FastAPI is the right size for this project.

Q36: Why not use WebSockets for the chat?

The current chat is request-response: send question, get answer. WebSockets would enable streaming (token-by-token output from the LLM), which improves perceived latency. But: (1) Cerebras SDK may not support streaming, (2) Adds complexity (connection management, reconnection logic), (3) The answer is usually short (1-3 paragraphs), so the user doesn't wait long. Future improvement: Add WebSocket streaming for the analysis pipeline (stream each section as it's generated).

K. Code Quality & Patterns

Q40: What design patterns did you use?

(1) Repository pattern: github_api.py abstracts GitHub API calls behind a clean interface. (2) Strategy pattern: db_utils.py gracefully degrades — the same code works with or without PostgreSQL. (3) Facade pattern: main.py orchestrates fetcher, analyzer, and DB behind a single generate_repo_analysis() function. (4) Cache-aside pattern: Check cache first, on miss fetch + store. (5) Builder pattern: build_hybrid_prompt() constructs a complex prompt from multiple data sources.

Q41: How do you manage state in the frontend?

Server state: Fetched via API and stored in React useState. The analysisCache Map in client.js acts as a global cache. UI state: Component-local useState for things like zoom level, chat input, tree expand/collapse. No global state library: The app is simple enough that prop drilling + local state works. If it grew, I'd use Zustand or React Context for shared state.

Q42: How do you handle loading states and UX?

Analysis loading: Full-page spinner with "Analyzing repository..." message. Backend takes ~15 sec, so the spinner prevents user confusion. Chat loading: "Thinking..." message in chat panel. Error states: Red error banner with specific message (e.g., "Repository not found", "Rate limit exceeded"). Empty states: Graceful messages when no data is available. Optimistic updates: Not used — the analysis is too expensive to predict.

Q43: How would you add unit tests to this project?

Backend: Use pytest + httpx.AsyncClient for API tests. Mock Cerebras and GitHubMCP with unittest.mock. Test section parser with various inputs. Test prompt builder with mock data. Frontend: Use Vitest (works with Vite) + @testing-library/react. Test component rendering, user interactions, API client caching. E2E: Playwright for full browser tests.

Q44: What's the most complex bug you fixed in this project?

The "0 source files" bug: The initial repo_fetcher.py only read top-level files. Repos like Flask have source code in src/flask/*.py. The LLM returned "No source files found" because the prompt had empty source data. Fix: _fetch_code_files_recursive() scans all directories recursively. The "code blocks skipped" bug: MarkdownRenderer was processing inline code (`code`) before code blocks (```code```), consuming backticks. Fix: parse code blocks first, then inline code on remaining text. The "DB updated_at" bug: Schema had updated_at column but UPSERT query didn't set it, causing INSERT failures. Fix: removed the column from schema.

Q45: If you had to rebuild this from scratch, what would you do differently?

(1) Start with TypeScript — the type safety pays off as the codebase grows. (2) Use embeddings from day one — even a simple TF-IDF search would improve chat quality. (3) Add streaming — WebSocket for real-time LLM output. (4) Use a task queue — Celery for background analysis generation. (5) Better testing — mock external services from the start. (6) Structured logging — not print statements. (7) Docker — containerize backend + DB for reproducible setup.
