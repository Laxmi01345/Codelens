1 System Overview

CodeLens is a GitHub repository analysis tool. A user pastes a repo URL, and the system shallow-clones the repository, reads all source and config files locally, builds a 4-layer hierarchical index (file metadata, AST structure, dependency graph, code chunks), generates a comprehensive 5-section architecture document using a single LLM call, caches it in PostgreSQL, and displays it in a modern dark-theme UI with zoomable Mermaid diagrams and an interactive chat powered by hybrid search (BM25 + embeddings + cross-encoder re-ranking) with streaming and conversation memory.

2 Why This Design

Why Shallow Git Clone Instead of GitHub API?

✓ Shallow Clone Approach (What We Use)
  • Complete file access — no depth or file count limits
  • Full file content — no truncation
  • No API rate limits — reads from local filesystem
  • Fast — shallow clone takes 3-5 seconds
  • Works for repos of any size
✗ GitHub REST API (Previous Approach)
  • Depth limited to 3 levels
  • Max 15 source files per directory
  • Files truncated to 2000 characters
  • 5000 requests/hour rate limit
  • Slow for large repos (serial API calls)

Why 4-Layer Hierarchical RAG?

Token efficiency + full awareness. The old approach sent all files to the LLM (50K+ tokens), causing context rot and high costs. The 4-layer approach sends file metadata + AST structure always (~3K tokens for full awareness), then retrieves dependencies + code chunks only when relevant (~5K tokens via BM25). Total: ~8K tokens per query with better output quality.

Why Cerebras?

Free tier. The project budget is zero. Cerebras offers a generous free API tier with the zai-glm-4.7 model. It's fast (optimized inference) and supports both chat completions and tool-use. No paid providers, no credit card.

Why Plain JavaScript (not TypeScript)?

Speed of iteration. The frontend is a relatively simple SPA — URL input, markdown rendering, a tree view, a chat panel. TypeScript adds type-checking overhead that isn't needed for this scope. Plain JSX in Vite works out of the box. All files are .jsx / .js.

Why PostgreSQL is Optional?

Zero-config local development. The system checks DB_AVAILABLE at startup. If PostgreSQL isn't running or psycopg2 isn't installed, every DB operation returns None or skips silently. The frontend analysisCache Map prevents duplicate requests within a session. This means developers can run the project without setting up a database.

Why No README Fallback?

Many repos have no README or have an empty one. Instead of failing, the system falls back through: GitHub description → topics array → package.json description → pyproject.toml description → source file docstrings. This was added after testing with repos like thrashr888/no-readme.

Why Shallow Clone Instead of API?

The original approach used GitHub API to fetch files, but had hard limits: depth capped at 3 levels, max 15 source files per directory, files truncated to 2000 chars, and 5000 requests/hour rate limit. The fix: repo_cloner.py does a shallow clone (git clone --depth 1), reads all files from the local filesystem, then cleans up. This gives complete access to every file with no limits.

Why Regex-Based AST Parsing?

The AST parser uses regex patterns instead of Python's ast module. This is a deliberate tradeoff:

Multi-Language Support

Python's ast module only parses Python. Regex patterns work across 6 languages (Python, JS, TS, Go, Rust, Java) with one implementation.

Sufficient Accuracy

For RAG context building, we don't need perfect AST - we need function signatures, class definitions, and import statements. Regex captures these reliably.

No Dependencies

Native ast module requires tree-sitter or language servers for multi-language. Regex is stdlib only - zero install, zero cost.

Interview Talking Point

"We chose regex for breadth over depth - a pragmatic tradeoff for a hackathon. In production, we'd use tree-sitter for full AST fidelity."

# analysis/ast_parser.py - Regex patterns per language
def _parse_python(content, ast):
    # Function definitions: def function_name(args):
    func_pattern = re.compile(r'^def\s+(\w+)\s*\((.*?)\)', re.MULTILINE)
    # Class definitions: class ClassName(BaseClass):
    class_pattern = re.compile(r'^class\s+(\w+)\s*(?:\((.*?)\))?', re.MULTILINE)
    # Imports: import X / from X import Y
    import_pattern = re.compile(r'^(?:from\s+(\S+)\s+)?import\s+(.+)', re.MULTILINE)
    
    for match in func_pattern.finditer(content):
        ast.functions.append(FunctionDef(
            name=match.group(1),
            args=match.group(2).split(","),
            line=content[:match.start()].count("\n") + 1,
        ))
    # Similar for classes, imports, exports...

class QueryExpander:

2. Code Property Graph

Combines AST + Control Flow + Data Flow in one graph.

# analysis/code_property_graph.py
class CodePropertyGraph:
    # Node types:
    #   FUNCTION, CLASS, CALL, VARIABLE
    
    # Edge types:
    #   DEFINES, CONTAINS, CALLS

    def get_impact_analysis(self, func):

3. Multi-hop Retrieval

Follows call chains to find related code the user might need.

# analysis/multi_hop_retrieval.py
class MultiHopRetriever:
    def retrieve(self, query, hops=2):
        # Hop 1: Direct semantic search
        results = search(query)
        
        # Hop 2: Find callers/callees
        for result in results:
            callers = cpg.get_callers(result.name)
            callees = cpg.get_callees(result.name)
            results.extend(callers + callees)
        
        return deduplicate(results)

# Example:
# Query: "How does login work?"
# Hop 1: Find "login" function
# Hop 2: Find what "login" calls
#   → validate_password, create_session

4. Re-ranking

Cross-encoder re-ranks top-20 results to top-5 for precision.

# analysis/reranking.py
class CrossEncoderReranker:
    def rerank(self, query, results, top_k=5):
        # Cross-encoder scores (query, doc) pairs
        pairs = [(query, doc) for doc in results]
        scores = cross_encoder.predict(pairs)
        
        # Blend: 70% cross-encoder + 30% original
        for result, score in zip(results, scores):
            result["final_score"] = 0.7 * score + 0.3 * result["score"]
        
        return sorted(results)[:top_k]

Complete Retrieval Pipeline

# Full pipeline: Query → Results
def retrieve_context(query, context):
    # 1. Query Expansion (3 queries)
    queries = query_expander.expand(query)
    
    # 2. Multi-hop Retrieval (2 hops)
    all_results = []
    for q in queries:
        results = multi_hop.retrieve(q, hops=2)
        all_results.extend(results)
    
    # 3. Re-ranking (top-20 → top-5)
    reranked = reranker.rerank(query, all_results, top_k=5)
    
    return reranked

# Split by headers, extract content between them
for i, header in enumerate(headers):
    start = text.index(header)
    end = text.index(headers[i+1]) if i+1 < len(headers) else len(text)

6 Streaming & Conversation Memory

Server-Sent Events (SSE)

HTTP streaming via /api/chat/stream. Tokens arrive as they're generated - users see text appear in real-time.

// Frontend consumption
const response = await fetch("/api/chat/stream", {
    method: "POST",
    body: JSON.stringify({ repo_url, question, history })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const text = decoder.decode(value);
    // Parse SSE: "data: chunk\n\n"
    appendToChat(text.replace("data: ", ""));
}

WebSocket Streaming

Persistent connection via /api/ws/chat. Bidirectional - sends chunks as JSON messages.

// Frontend consumption
const ws = new WebSocket("ws://localhost:8000/api/ws/chat");

ws.send(JSON.stringify({
    repo_url, question, stream: true
}));

ws.onmessage = (event) => {
    const msg = JSON.parse(event.data);
    if (msg.type === "chunk") {
        appendToChat(msg.content);
    } else if (msg.type === "stream_end") {
        console.log("Complete answer:", msg.answer);
    }
};

Conversation Memory

Both HTTP and WebSocket maintain conversation history (last 4 exchanges). Each query includes prior context so the LLM understands follow-up questions.

// WebSocket: per-connection memory
conversation_history = []
while True:

    response = await chat_with_repo(
        data["repo_url"], data["question"],
        history=conversation_history,  // prior messages
    )
    // Update memory
    conversation_history.append({"role": "user", "content": question})
    conversation_history.append({"role": "assistant", "content": answer})
    conversation_history = conversation_history[-8:]  // keep last 4 exchanges

10 LLM Integration (Cerebras)

For Analysis

One call, all 5 sections. The hybrid_analyzer.py builds a 4-layer context prompt containing file metadata, AST structure, dependencies, and code chunks. Cerebras generates all sections in one response. The output is parsed by parse_sections() which looks for ## Section N: or ## Name headers.

For Chat

Smart layer selection. chat_with_repo() detects query type (summary vs specific) and builds optimal context. Summary queries get ~3K tokens (Layers 1-2 only). Specific queries get ~8K tokens (all 4 layers with hybrid search: BM25 + embeddings + RRF + re-ranking). Single LLM call per question with streaming support.

Model

zai-glm-4.7 — the only Cerebras model with tool-use support. Used for both analysis and chat. Free tier, no rate limits for reasonable usage.

API Usage

    model="zai-glm-4.7",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt},
    ],
    max_tokens=4096,
)

answer = response.choices[0].message.content

19 Interview Questions & Answers

Every question an interviewer could ask about this project, from architecture to implementation details.

A. System Design & Architecture

Q1: Walk me through the high-level architecture of this project.

CodeLens is a three-tier system: React/Vite SPA (frontend) → FastAPI backend (orchestration) → External services (Git Clone, Cerebras LLM, SQLite FTS5, PostgreSQL). The frontend sends a GitHub URL to the backend. The backend shallow-clones the repository, reads all files locally, builds a 4-layer hierarchical index (file metadata, AST structure, dependency graph, code chunks), generates 5 analysis sections with a single LLM call, caches the result in PostgreSQL, and returns it. For chat, the 4-layer index provides efficient context: Layers 1-2 (always sent) give full codebase awareness (~3K tokens), while Layers 3-4 (BM25 search) retrieve only relevant code (~5K tokens). The frontend renders it as a wiki page with zoomable Mermaid diagrams and markdown content.

Q2: Why did you choose a hybrid approach with 4-layer RAG?

The first version used an agentic loop — the LLM would decide which MCP tool to call, execute it, get the result, and loop (8+ sequential LLM calls, 2-3 minutes per analysis). I replaced it with a hybrid approach: one LLM call generates all 5 sections at once (~15 seconds). For chat, I added 4-layer hierarchical RAG with smart query detection: summary queries use only Layers 1-2 (~3K tokens, 94% savings), while specific queries use all 4 layers (~8K tokens, 84% savings) with BM25 for code retrieval. Why: (1) predictable latency, (2) massive token savings, (3) full codebase awareness for summaries, (4) detailed code for specifics, (5) works with Cerebras free tier, (6) simpler codebase.

Q3: What are the trade-offs of the 4-layer approach?

Pros: Fast (~8K tokens per query), cheap, predictable, full codebase awareness via Layers 1-2, relevant details via BM25 in Layers 3-4. Cons: (1) The LLM can't dynamically explore the codebase — it only sees what the index contains, so it might miss important context in very large repos. (2) BM25 relies on exact keyword matching — conceptual queries like "how does authentication work" might miss relevant code if function names don't match. (3) Index build time adds ~1-2 seconds per repo. Mitigation: Layers 1-2 provide complete structure awareness, and the AST parser extracts function signatures that often contain descriptive names.

Q4: How does this system handle scalability?

Per-request: Each analysis takes ~15 sec (git clone + LLM call). The DB cache means repeat requests are instant. Concurrency: FastAPI is async, so it handles multiple requests without blocking. Git clone is the main bottleneck for concurrent analyses (each uses disk I/O). Horizontal scaling: The backend is stateless — just add more instances behind a load balancer. The DB is the shared state. LLM scaling: Cerebras handles inference; we don't control it, but their free tier is generous for moderate usage.

Q5: What improvements have been made since the initial version?

(1) Streaming: Implemented SSE and WebSocket streaming for real-time token-by-token output. (2) Hybrid search: Added embeddings (sentence-transformers) alongside BM25 with Reciprocal Rank Fusion. (3) Cross-encoder re-ranking: ms-marco-MiniLM-L-6-v2 for precision after initial retrieval. (4) Background jobs: Celery + Redis for non-blocking analysis. (5) Vector DB: Qdrant for persistent embedding storage with filtering. (6) Monitoring: Prometheus + Grafana for metrics and dashboards. (7) Advanced RAG: Query expansion, multi-hop retrieval, Code Property Graph, call graph analysis. (8) Docker: Full Docker Compose setup with 8 services. (9) Config files in index: .gitignore, package.json, etc. now indexed for complete context.

B. Backend Design

Q6: How does the repository data fetching work?

repo_cloner.py performs a shallow git clone (git clone --depth 1 --filter=blob:limit=100k) to a temp directory. read_all_files() walks the cloned directory, reading all source files (.py, .js, .ts, .go, etc.) and config files (package.json, requirements.txt, etc.) from the local filesystem. No API rate limits, no file truncation, no depth limits. After reading, the temp directory is cleaned up. github_client/github.py is only used for repo validation and fetching issues.

Q7: How do you handle GitHub API rate limits?

The system minimizes API usage by: (1) Using shallow git clone for file reading — no API calls needed, (2) Only calling GitHub API for repo validation and issues fetching, (3) Caching results in PostgreSQL so repeat requests don't hit the API at all. Without authentication: 60 requests/hour. With a token: 5000/hour. Since we only use the API for validation + issues (2-3 calls per analysis), rate limits are rarely hit.

Q8: Explain the database schema and why you chose that design.

Single table repo_analysis with repo_url as primary key. Each column stores one analysis section as TEXT. UPSERT on conflict updates all fields. Why TEXT type: Analysis sections can be long (markdown, mermaid code), and TEXT has no length limit. Why no normalized tables: The data is always accessed as a whole — we never query "just the tech stack for repo X". One row per repo is simpler and faster. Why no updated_at: Initial version had it but the column wasn't being set, causing INSERT failures. Removed it since created_at is sufficient for cache invalidation.

Q9: Why is the database optional? How does the fallback work?

For local development, requiring PostgreSQL adds setup friction. The system checks: (1) Is psycopg2 installed? (2) Can we connect? If either fails, DB_AVAILABLE = False. Every DB operation checks this flag and returns None or skips silently. The frontend cache (analysisCache Map) prevents duplicate requests within a session. Without DB, each page load regenerates the analysis (~15 sec), but it works.

Q10: How does the section parser work?

hybrid_analyzer.py calls Cerebras, gets the full response, then parse_sections() splits it. It uses regex to find section headers: ## Section N: Name, ## Name, or # Name. Each section's content is everything between one header and the next. If a section isn't found, it defaults to "Section not generated." The parser also strips the first header line from each section's content (since the wiki page renders the header separately).

Q11: How does the file reading work?

repo_cloner.py does a shallow clone (git clone --depth 1 --filter=blob:limit=100k) to a temp directory. read_all_files() uses os.walk() to traverse the entire directory tree, skipping ignored dirs (.git, node_modules, __pycache__, etc.). It reads all source files (by extension) and config files (by name match) into dictionaries. Files over 100KB are skipped. After reading, the temp directory is cleaned up. This gives complete access to every file with no depth or count limits.

C. LLM Integration

Q12: How do you prevent LLM hallucination?

Three layers: (1) Strict system prompt: Rules like "every statement must cite a file path", "use ONLY provided data", "say 'Not found' for missing info". (2) Constrained input: We only feed the LLM actual file contents and directory structures — no vague descriptions. (3) Post-processing: The section parser checks for empty/missing sections and falls back to defaults. The LLM model zai-glm-4.7 also tends to be conservative and follow instructions well.

Q13: How do you handle context window limitations?

The 4-layer hierarchical approach with smart query detection solves this: (1) Summary queries: Only Layers 1-2 (~3K tokens) — file metadata + AST structure provide full codebase awareness without sending actual code, (2) Specific queries: All 4 layers (~8K tokens) — includes dependencies + code chunks retrieved via BM25, (3) Smart detection: The system automatically detects if a question needs full code context or just structure overview. (4) 94% savings for summary queries, 84% for specific queries.

Q14: Why Cerebras specifically? What about OpenAI, Anthropic, etc.?

Budget constraint: The project uses zero paid services. Cerebras offers a free API tier with decent rate limits. OpenAI/Anthropic require paid API keys. Model choice: zai-glm-4.7 is the only Cerebras model with tool-use support (though we only use chat completions now). Speed: Cerebras has optimized inference infrastructure. Trade-off: Smaller model means lower quality outputs compared to GPT-4 or Claude, but the strict prompt compensates. Data advantage: With git clone, we can feed the LLM complete file contents instead of truncated API responses.

Q15: How would you switch to a different LLM provider?

llm_utils.py wraps the Cerebras client. To switch: (1) Create a new client class for the target provider (e.g., OpenAIClient), (2) Implement the same chat.completions.create() interface, (3) Update the model name and API key env var. The prompts in hybrid_prompts.py are provider-agnostic — they're just strings. The only Cerebras-specific code is in main.py (chat) and hybrid_analyzer.py (analysis).

Q16: How do you parse the LLM output into structured sections?

The LLM is prompted to output sections with headers like ## Section 1: Purpose & Scope. The parser uses regex patterns: r'## Section \d+: (.+?)$', r'## (.+?)$', r'# (.+?)$'. It finds all headers, sorts by position, and extracts content between consecutive headers. If the LLM outputs in a slightly different format (e.g., missing "Section N"), the fallback patterns still catch it. This makes the parser robust to minor LLM output variations.

D. Frontend Architecture

Q17: How does the frontend prevent duplicate API calls?

api/client.js maintains an in-memory analysisCache (a Map). Before every fetch, it checks if the URL+forceRefresh key exists in the cache. If yes, returns the cached result. If no, fetches and stores. Also: React StrictMode was removed from main.jsx because it causes double-rendering in dev mode, which triggers duplicate API calls. The cache key includes force_refresh so manual refreshes bypass it.

Q18: How does the Mermaid diagram zoom/pan work?

MermaidDiagram.jsx uses CSS transforms: transform: scale(${zoom}) translate(${panX}px, ${panY}px). Zoom is controlled by: (1) buttons (+/-/reset), (2) Ctrl+Scroll wheel (with event.preventDefault() to prevent page zoom), (3) pinch on trackpad. Pan uses onMouseDown/Move/Up events tracking delta movement. The fullscreen modal uses a fixed-position overlay with backdrop-filter: blur(8px) and ESC key listener to close.

Q19: How does the MarkdownRenderer handle code blocks with tree characters?

Early bug: code blocks were being skipped entirely because the regex for inline code (`code`) was consuming backticks before the code block parser ran. Fix: parse code blocks first (match ```...```), extract their content, wrap in <pre><code>, then process inline markdown on non-code text. Tree characters (├──, └──, │) render correctly inside <pre> blocks because whitespace is preserved.

Q20: Why remove React StrictMode?

React StrictMode intentionally double-invokes effects and state updates in development to catch bugs. This caused analyzeRepository() to fire twice on mount, sending two POST requests to the backend. The second request would either hit the DB cache (wasteful) or trigger a second LLM call (expensive). Removing StrictMode is acceptable because: (1) the app is simple enough that double-rendering bugs are unlikely, (2) the performance cost of duplicate API calls outweighs StrictMode's benefits, (3) production builds don't have StrictMode double-rendering anyway.

Q21: How does the WikiPage handle navigation without a header bar?

The WikiPage has no top header — it fills the entire viewport. Navigation is via: (1) WikiTreeView sidebar (collapsible folder tree + section links), (2) Breadcrumb at the top (CodeLens / owner/repo), (3) Back button to return to HomePage. The tree view uses onClick to scroll to sections via document.getElementById(sectionId).scrollIntoView(). The chat panel floats at the bottom with position: fixed.

E. API Design

Q22: What are the API endpoints and their responsibilities?

POST /api/analysis: Accepts { repo_url, force_refresh }. Checks DB cache, shallow-clones repo if miss, reads all files locally, generates LLM analysis, stores in DB, returns all sections. GET /api/analysis/{repo_url}: Retrieves cached analysis from DB (read-only). POST /api/chat: Accepts { repo_url, question }. Builds context from cached analysis + key files, makes single LLM call, returns answer. GET /api/issues/{repo_url}: Fetches GitHub issues via API (only endpoint that uses GitHub API for data). All endpoints return JSON. CORS allows localhost:5173 and localhost:3000.

Q23: Why use POST for analysis instead of GET?

GET requests should be idempotent and cacheable. Analysis is expensive (LLM call, git clone) and not idempotent (force_refresh bypasses cache). POST allows: (1) request body with force_refresh flag, (2) clear indication that the server performs side effects (LLM call, DB write), (3) no URL length limits (GitHub URLs can be long). GET /api/analysis/{url} is available for read-only cache lookups.

Q24: How does error handling work across the stack?

Backend: Each function catches exceptions and returns meaningful errors. GitHubAccessError for repo access issues. FastAPI HTTPException with status codes (404 for not found, 500 for internal errors). DB errors are logged but don't crash the request (graceful degradation). Frontend: client.js checks response.ok and throws with the error detail. Components catch errors and display them in the UI (e.g., "Failed to analyze repository"). The chat panel shows error messages inline.

F. Security

Q25: How do you handle API keys and secrets?

Backend: Keys stored in .env file (gitignored). Loaded via python-dotenv. Never hardcoded. CEREBRAS_API_KEY and GITHUB_TOKEN are the two secrets. Frontend: No secrets — it only talks to the FastAPI backend. DB credentials: Also in .env, with sensible defaults for local dev. Production: Use environment variables injected by the deployment platform (e.g., Vercel, Railway).

Q26: What CORS configuration do you use?

allow_origins=["http://localhost:5173", "http://localhost:3000"] — only the frontend dev servers. allow_methods=["*"] and allow_headers=["*"] for flexibility during development. allow_credentials=True to support cookies if needed. Production: Would restrict origins to the actual deployed frontend URL.

Q27: Is there any input validation?

Pydantic models: AnalysisRequest and ChatRequest validate input types. repo_url is a string, force_refresh is a boolean. URL validation: validate_repo() checks that the URL points to a valid, accessible GitHub repository. SQL injection: Not possible — we use parameterized queries (%s placeholders) with psycopg2. XSS: The frontend renders markdown as HTML — MarkdownRenderer doesn't use dangerouslySetInnerHTML for user input, only for LLM-generated markdown.

G. Performance & Optimization

Q28: How do you optimize the analysis pipeline for speed?

Shallow clone: git clone --depth 1 downloads only the latest snapshot (~3-5s). Local file reads: Reading from filesystem is instant vs serial API calls. Single LLM call: All 5 sections in one prompt (vs 8+ calls in the old agentic approach). DB caching: Repeat requests are instant. Frontend cache: In-memory Map prevents duplicate requests. Smart file selection: get_relevant_files_for_prompt() ranks files by importance (hub modules, complexity, imports) and selects top 20-30 for the LLM prompt.

Q29: What are the bottlenecks in this system?

Git clone: Network-dependent, takes 3-5 seconds for shallow clone. Large repos with huge blobs may take longer (filtered at 100KB). LLM latency: Cerebras inference takes ~10-15 seconds for a large prompt. Prompt size: For repos with many files, the LLM prompt can get very large. Smart file selection mitigates this. DB: PostgreSQL writes are fast (~5ms) but reads with cold cache are slow (full analysis regeneration). Frontend: Mermaid rendering can be slow for complex diagrams (~2-3 sec).

Q30: How would you handle 100 concurrent users analyzing different repos?

Current bottleneck: Git clone + LLM inference. Each analysis takes ~15 sec (clone + LLM). Solutions: (1) Request queuing with rate limiting, (2) Aggressive DB caching (most repos will be repeat requests), (3) Horizontal scaling of FastAPI instances, (4) Background job queue (Celery/RQ) for analysis generation, (5) Shared file cache across instances. Since we use git clone instead of GitHub API, there are no API rate limits to worry about.

H. Testing & Quality

Q31: How would you test this system?

Unit tests: Test parse_sections() with various LLM output formats. Test build_hybrid_prompt() with mock repo data. Test MarkdownRenderer with edge cases. Integration tests: Test the full API pipeline with a mock git clone and mock LLM. Test DB operations with a test database. E2E tests: Use Playwright/Cypress to test the full flow: enter URL → see analysis → use chat. Mocking: Mock Cerebras API (expensive to call in tests) and git clone (use local test repos).

Q32: What are the main edge cases you've handled?

(1) No README: Fallback to GitHub description, topics, package.json. (2) Empty/private repos: Git clone fails, caught and surfaced. (3) DB unavailable: System works without caching. (4) LLM output format variations: Parser uses multiple regex patterns. (5) Large repos: Smart file selection ranks by importance, sends top 20-30 to LLM. (6) Invalid URLs: Pydantic validation + GitHub API check. (7) Network errors: try/except with meaningful error messages. (8) Missing git: Dockerfile installs git, local dev requires git installed.

I. Key Technical Decisions

Q33: Why plain JavaScript instead of TypeScript?

Trade-off: type safety vs development speed. For this project: (1) The frontend is relatively simple (5 components, 2 pages), (2) No team to benefit from type contracts, (3) Vite works with plain JSX out of the box, (4) Adding TypeScript means config files (tsconfig.json), type annotations on every component, and stricter build steps. If the project grows to 20+ components, TypeScript would be worth adding.

Q34: How do you handle search — BM25 vs embeddings?

We use both. The hybrid retriever combines: (1) BM25 for exact keyword matching (fast, ~5ms), (2) Embeddings (sentence-transformers all-MiniLM-L6-v2) for semantic understanding (~200ms), (3) Reciprocal Rank Fusion to merge results from both, (4) Cross-encoder re-ranking (ms-marco-MiniLM-L-6-v2) for precision — top-20 → top-5. Why both: BM25 excels at exact matches ("auth.py", "login function"), while embeddings catch semantic relationships ("user sessions" matches "auth logic"). The fusion gives the best of both worlds.

Q35: Why use FastAPI instead of Flask or Django?

FastAPI advantages: (1) Native async support (critical for git clone + LLM calls), (2) Auto-generated OpenAPI docs, (3) Pydantic request/response validation, (4) Type hints as documentation. Flask: No native async, would need aiohttp or celery for background tasks. Django: Too heavy — includes ORM, admin, auth that we don't need. FastAPI is the right size for this project.

Q36: How does streaming work?

Two streaming modes implemented: (1) SSE (Server-Sent Events): POST /api/chat/stream returns text/event-stream. The frontend uses ReadableStream to consume tokens as they're generated. (2) WebSocket: WS /api/ws/chat provides bidirectional communication. Chunks arrive as JSON {"type": "chunk", "content": "..."} messages. Both modes maintain conversation history (last 4 exchanges) for follow-up context. The Cerebras SDK supports streaming natively via stream=True.

K. Code Quality & Patterns

Q40: What design patterns did you use?

(1) Repository pattern: github_client/github.py abstracts GitHub API calls behind a clean interface. (2) Strategy pattern: db_utils.py gracefully degrades — the same code works with or without PostgreSQL. (3) Facade pattern: main.py orchestrates cloner, analyzer, and DB behind a single generate_repo_analysis() function. (4) Cache-aside pattern: Check cache first, on miss fetch + store. (5) Builder pattern: build_hybrid_prompt() constructs a complex prompt from multiple data sources. (6) Layered architecture: 4-layer RAG with always-on layers (1-2) and question-driven layers (3-4). (7) Index pattern: SQLite FTS5 for BM25 search over code chunks.

Q41: How do you manage state in the frontend?

Server state: Fetched via API and stored in React useState. The analysisCache Map in client.js acts as a global cache. UI state: Component-local useState for things like zoom level, chat input, tree expand/collapse. No global state library: The app is simple enough that prop drilling + local state works. If it grew, I'd use Zustand or React Context for shared state.

Q42: How do you handle loading states and UX?

Analysis loading: Full-page spinner with "Analyzing repository..." message. Backend takes ~15 sec, so the spinner prevents user confusion. Chat loading: "Thinking..." message in chat panel. Error states: Red error banner with specific message (e.g., "Repository not found", "Rate limit exceeded"). Empty states: Graceful messages when no data is available. Optimistic updates: Not used — the analysis is too expensive to predict.

Q43: How would you add unit tests to this project?

Backend: Use pytest + httpx.AsyncClient for API tests. Mock Cerebras and GitHubMCP with unittest.mock. Test section parser with various inputs. Test prompt builder with mock data. Frontend: Use Vitest (works with Vite) + @testing-library/react. Test component rendering, user interactions, API client caching. E2E: Playwright for full browser tests.

Q44: What's the most complex bug you fixed in this project?

The "0 source files" bug: The initial repo_fetcher.py used GitHub API with depth limit 3 and 15 files per directory. Repos like Flask have source code deep in src/flask/*.py subdirectories. The LLM returned "No source files found" because the prompt had empty source data. Fix: switched to shallow git clone approach — repo_cloner.py clones the repo and reads all files from local filesystem with no depth or count limits. The "context rot" bug: The old approach sent all files to the LLM (50K+ tokens), causing the model to lose focus and produce lower quality output. Fix: implemented 4-layer hierarchical RAG — Layers 1-2 provide full structure awareness (~3K tokens), Layers 3-4 retrieve only relevant code via BM25 (~5K tokens). The "code blocks skipped" bug: MarkdownRenderer was processing inline code (`code`) before code blocks (```code```), consuming backticks. Fix: parse code blocks first, then inline code on remaining text.
